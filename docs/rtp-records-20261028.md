# Instrumented RTP score and record checkpoint

This additive checkpoint narrows the software fault mechanism using accepted DM, DP and DT captures, then records a separate reversible RAM-limit comparison. It preserves the earlier rejected writer preparations and their cleanups. The first two fixtures contain read-only controller observations. The third contains the accepted finite40→200 intervention, restoration to40 and two clean observations; it does not establish prevention. There is no code patch, persistent hook, firmware installation or demonstrated fix. All public verification is offline.

## Reproducible scientific subset

The [public fixture](../fixtures/rtp-dp40-dm.json) contains 48 bounded controller windows plus five compact34-byte checkpoints, totaling4,986 raw bytes. It includes scientific transfer/key timestamps, source addresses and counters. Device identity, boot UUID, filesystem binding metadata, authentication, local network state and transport envelopes are absent. It is a deliberately selected scientific subset, not a reproduction or reauthentication of the private transport/readiness evidence.

From a fresh clone:

```sh
python3 tools/verify_rtp.py
python3 -O tools/verify_rtp.py
python3 -m unittest discover -s tests -v
```

The [fixture builder](../tools/build_rtp_fixtures.py) documents the whitelist used to derive this subset from retained receipts. It reads files from an explicitly supplied evidence root and never imports device tooling or makes target requests. The standalone verifier checks exact sizes/hashes/canonical Base64, fixed window order, OUT/IN completion and phase, monotonic read brackets, RT halfwords, compact packing, key ordering, global-versus-retained count arithmetic, record reconstruction and conservative scope flags. Mutated raw data, counts, addresses, phases, timestamps, bool-as-count values and physical/atomic overclaims are tested as refusals.
