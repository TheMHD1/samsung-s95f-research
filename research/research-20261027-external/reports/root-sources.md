# Root-source research and claim audit — 2026-10-27 UTC

The supplied projects do not provide a demonstrated permanent fix for this TV's blackout. Existing target evidence already establishes host-assisted root and repeated owner-confirmed recovery after selecting populated Apps and issuing one stock operation 41/mode 2. Root acquisition is therefore an enabling tool, not the missing repair. The useful external deltas are a specific application boot hook worth investigating offline, compatibility/runtime changes upstream, concrete defects in the untethered fork, and a separate S95F-family research lineage reporting that compositor capture can omit video.

Scope: GitHub/web retrieval and local source inspection only. No TV connection, TV command, exploit installation, source execution, native probe, firmware patch or flash was performed. The baseline was `CURRENT-INVESTIGATION.md`, `RECOVER-PANEL.md`, the local access adapter, and the existing source trees. After [independent audit](../reviews/independent-audit.md), this revision also incorporates the previously retained exact-target managed-substitution/socket tests; those tests were omitted from the first report revision. The target adapter pins **QN77S95FAFXZC / T-RSMFAKUC-0090-REL-202607141953**; the investigation identifies kernel **5.4.261** and panel **CY-AF077FLLV2H**. These exact target records outrank a repository's generic compatibility or impossibility statement.

## 1. Archive-root mechanism: already relevant, not new target access

Upstream's actual common C# payload checks effective SETGID/SYS_ADMIN capabilities, creates a private mount namespace, makes the mount tree private, overlays its verification-key and passwd views, invokes the existing capability-bearing archive launcher, and detaches both overlays in `finally`. There are no kernel addresses in this route. This supports the distinction between temporary userland acquisition and the separate model-specific kernel routes. It does not prove arbitrary later commands are reversible or that every descendant has exited. [Common payload, lines19–98](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/payloads/common/SamsungTvArchiveRoot.cs#L19-L98).

The host controller authenticates frames and rejects a connecting agent unless uid, euid, gid and egid are all zero when `require_root` is enabled. This is stronger than merely printing a success string or observing a shell exit code. [Root-agent gate, lines495–518](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/src/samsung_tv_root/root_agent.py#L495-L518). The existing S95F adapter already uses this source family and has independent model/build checks. There is no reason here to replace working target acquisition with the QN90F Mali exploit or QN90B physical-memory exploit.

New upstream delta: runtime selection now supports an active `/usr/share/dotnet.tizen/netcoreapp` symlink fallback when Samsung's signed host rejects `--list-runtimes`, plus explicit runtime selection; capability checks and tar-option checks remain separate. .NET3.1 project files, packaged OpenSSL environment handling and a retry of a noisy timing-oracle calibration were also added. [Runtime/preflight, lines68–137](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/src/samsung_tv_root/archive_root.py#L68-L137), [CLI runtime argument, lines1061–1070](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/src/samsung_tv_root/cli.py#L1061-L1070), [SDB timing calibration, lines200–231](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/src/samsung_tv_root/sdb.py#L200-L231).

**Target limit:** the local working tree already contains its own runtime-enumeration adaptation. A newer HEAD is not automatically a better target-specific implementation. The common C# archive payload is byte-identical between the local working tree and reviewed upstream. An update should be an offline reviewed merge preserving the exact build/identity gates; there is no root-access gap requiring deployment now.

## 2. Untethered boot: a plausible specific hook, unproved on S95F

The fork documents `app-boot-manager` launching an installed `dotnet-inhouse` app from writable package data. Its stated trigger combines `package_app_info.app_onboot` in `/opt/dbspace/.pkgmgr_parser.db` with the manifest's on-boot flag. Current instructions replace Gaming Hub service IL and change the component into a UI app. The documented hardware proof is QN55Q60BAFXZC/T-NKLBAKUC, kernel5.4.77 ARMv7/Tizen6.5. This is neither S95F proof nor a generic 2022–2026 compatibility matrix. [Trigger and deployment, lines53–120](https://github.com/levkropp/samsung-tv-root-untethered/blob/2b0629381b3eaf5a78f84332d630d6d4b10681e7/boot-agent/README.md#L53-L120).

Actual `RunChain` stages artifacts, builds a localhost SDB request, waits a bounded number of times for a session, fires one acquisition request, and polls for a timestamp-qualified text proof. The fork's common payload adds explicit staging/on-demand arguments but retains the private-namespace mechanism. Boot-time code writes a root proof then executes enabled modules from persistent `/opt`. [Program, lines827–1101](https://github.com/levkropp/samsung-tv-root-untethered/blob/2b0629381b3eaf5a78f84332d630d6d4b10681e7/boot-agent/Program.cs#L827-L1101), [archive payload, lines19–110](https://github.com/levkropp/samsung-tv-root-untethered/blob/2b0629381b3eaf5a78f84332d630d6d4b10681e7/payloads/common/SamsungTvArchiveRoot.cs#L19-L110), [module runner, lines20–78](https://github.com/levkropp/samsung-tv-root-untethered/blob/2b0629381b3eaf5a78f84332d630d6d4b10681e7/boot-agent/staging/build.py#L20-L78).

The localhost SDB path requires the Developer Mode host address to be loopback at SDB startup according to its Q60B tests. That changes the management path; a token relay then exposes localhost SDB to the LAN. The relay is created as a volatile systemd service by a boot module after root acquisition. Thus `/run` unit volatility is compatible with this design: the persistent trigger is the app/database entry, and the runtime service is rebuilt. [Operating model, lines145–201](https://github.com/levkropp/samsung-tv-root-untethered/blob/2b0629381b3eaf5a78f84332d630d6d4b10681e7/boot-agent/README.md#L145-L201), [bridge module, lines1–32](https://github.com/levkropp/samsung-tv-root-untethered/blob/2b0629381b3eaf5a78f84332d630d6d4b10681e7/modules/bridge-service/boot.sh#L1-L32).

The exact S95F already has relevant tests in [boot-suitability.summary](../../live-cast/boot-suitability.summary) (SHA-256 `0c015aad4a4493a544f0ca3566806fab181b8d8af482758f88a48e4404e55c97`) and [boot-socket-test.summary](../../live-cast/boot-socket-test.summary) (SHA-256 `597d46bad52ad5c4c94c39e67923d609a9d6d7e72f0b7d76eac165b554891f08`). Starting a child `/usr/bin/dotnet` was denied. The socket test additionally records `Loopback SDB bytes=0 frame=` and `LAN listener permitted`. Both record restoration of the original assembly with SHA-256 `3ce6c9b3eafd039728b2471e8349fedd5d3de5598ebec10d8425f716aef034e4`.

The retained [suitability runner](../../live-cast/boot-suitability.sh) and [socket runner](../../live-cast/boot-socket-test.sh) check `app_onboot|app_disable=false|false`, launch through `app_launcher -s`, and restore the assembly. Offline comparison must retain the recorded Developer Mode/SDB startup context rather than assume the Q60B loopback-host configuration was tested on S95F. **Remaining unknowns:** the automatic app-boot-manager launch edge and database trigger behavior, target host-IP policy at SDB startup, compatibility of the fork's handshake/staging/runtime with this app context, and complete cold-boot acquisition without the host. ## 3. DemonKingSwarn: useful negative results, incomplete impossibility proof

This is a QEF1A/RSLF/rosel ARMv7 report despite sharing kernel5.4.261 with the target. These facts can exclude a simple persistent systemd-unit drop; they do not exhaust consumers of writable package metadata. The fork's app-boot-manager mechanism is a distinct candidate. Neither author's result establishes S95F boot persistence or its impossibility. [Target identity lines142–167](https://github.com/DemonKingSwarn/samsung-tv-tizen-root/blob/ec5a8fcdc22e4014bde24a1970ce4cd4adc823de/ROOTING-RESEARCH.md#L142-L167), [persistence argument lines506–555](https://github.com/DemonKingSwarn/samsung-tv-tizen-root/blob/ec5a8fcdc22e4014bde24a1970ce4cd4adc823de/ROOTING-RESEARCH.md#L506-L555).

Its actual driver collects capability strings but replaces `_check_target` without validating those strings or tar's required option, then hard-codes runtime6.0. It preserves the upstream authenticated server, and retained JSON reports all four IDs0 with cleanup assertions. Those are inspectable author-supplied artifacts, not our independent replay. The monkey patch should not be transplanted into the target adapter. [Driver lines43–60](https://github.com/DemonKingSwarn/samsung-tv-tizen-root/blob/ec5a8fcdc22e4014bde24a1970ce4cd4adc823de/evidence/do_root.py#L43-L60), [root artifact](https://github.com/DemonKingSwarn/samsung-tv-tizen-root/blob/ec5a8fcdc22e4014bde24a1970ce4cd4adc823de/evidence/root-evidence.json#L1-L12).

## 4. Low-level/debug interfaces and rejected cross-model transfers

Upstream's QN90F profile specifies a tested RSMF build different from the exact target, architecture, Mali access and r48p0 requirements. Kernel version alone does not validate its kernel addresses, credential layout or exploit. The QN90B profile requires a different memory device/platform. Treat these as compatibility evidence requirements, not probes to run because root is already available. The QN90F display helper calls `libdeviced` public power/screen-state APIs. Its “confirmed” state describes API readback, not a light sensor or the target's stock operation41 controller lifecycle. Backup/rollback is mechanism-specific: namespace overlays disappear when the acquisition processes/mount references end; runtime unit masks disappear at reboot; persistent markers/app replacements/package-row changes require their original contents and metadata; raw-block patches require exact partition identity and byte backups and can prevent reaching the rollback shell. A “safe mode” flag or a host service disable does not restore those persistent changes. None should be introduced as part of diagnosing the established content-dependent fault.

The next reviewable output should be an **offline target hook applicability matrix beginning with the retained exact-target negative tests**, not an untethered installer or a permanent reset service. The current Apps-selected single-stock-restart recovery remains a demonstrated recovery with its existing limits; the external sources neither supersede it nor establish prevention.
