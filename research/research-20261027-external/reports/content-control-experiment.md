# Content-control experiment for the Home blackout

Recorded 2026-10-27 UTC. **Offline source/design only:** this work made no TV call, built or deployed no target helper, ran no new helper, and changed no firmware, UI, settings, recovery routine or current TV state. Source pins and local evidence hashes are in [source-inventory.json](../sources/content-control-experiment/source-inventory.json); the machine-readable proposal is [experiment-plan.json](../sources/content-control-experiment/experiment-plan.json).

## Decision

A useful new causal intervention is technically plausible but **not qualified for this S95F today**. Keep For You selected while a single focus-skipping EFL window remains alive, and change only its preallocated rectangle colors. Compare an actual pixel change against a timed sham in that same window. Separately, hold a fully opaque image fixed while changing Apps/For You underneath it. Together these remove much of the present page-selection/content confounding. They do not isolate OLED electrical load from the compositor or establish a final prevention method.

The pinned upstream probe supplies rectangle rendering, a notification-plane window and finite Ecore-loop exit. It does **not** supply the required timed in-place scene sequence, target ABI/session qualification, presentation timestamps or independent process deadline. Repeatedly launching it with different scenes would create/destroy windows at each treatment and leave the central composition/lifecycle confound. That is not the recommended primary A/B.

The practical gating question is whether any modest opaque candidate scene can keep **For You selected, physically visible and fresh-RT clean** long enough to begin the fixed-tab test. A gray or tiled scene is not assumed stable merely because Apps is stable. If that gate fails, this route has not created a usable experimental baseline; do not turn repeated recoveries into a search loop.

## What the pinned upstream code actually does

Pin: `chris-ritsen/samsung-tv-root` commit `3b97edf3762db7670585d73e29623dc56195bf98`, dated 2026-10-23 in the existing root-source inventory. These are reviewed local snapshot bytes, not a claim about newer upstream HEAD.

- [`Qn90fEflTextOverlayProbe.cs`](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/payloads/qn90f/Qn90fEflTextOverlayProbe.cs) creates Elementary window type 12, notification level 40, layer 900, alpha enabled, borderless, focus-skip, zero input rectangle, pass-events and an effect-disable auxiliary hint. Its fixed canvas is 1920×1080. A normal Evas layer alone is explicitly insufficient for the author's hardware-video composition.
- `SceneRenderer.RenderSceneFile` reads **once**, before showing the window. It accepts 1–256 rectangle/text/image/etc. objects and up to 1 MiB. `ShowRectangle` uses `evas_object_rectangle_add`, `ConfigureBox`, `evas_object_color_set`, move/resize/show. It does not implement a timed scene swap or retain a public object array for subsequent color updates.
- `Main` defaults to five seconds, permits raw `--seconds 0` for indefinite lifetime, and installs `ecore_timer_add` only for positive duration. The timer's return is unchecked. The `overlay_ready` line precedes `ecore_main_loop_begin`: it is a construction marker, not evidence of scanout or physical light. There are no monotonic presentation times.
- `RequestQuit` handles the timer and `Console.CancelKeyPress`/SIGINT through Ecore's thread-safe callback. This does not establish SIGTERM behavior or cleanup after a hung loop. Normal completion hides the window and exits; it intentionally avoids deleting the vendor EO window because the author observed double unref in this raw-client lifecycle. The imported `elm_shutdown` is not called.
- `ConfigureUiEnvironment` hard-codes owner identity, `/run/user/5001`, `wayland-0`, the TV profile and `wayland_shm`, with dmabuf disabled. The default diagnostic path is hard-coded under the author's `sdk_tools/qn90f-overlay`, creates directories and truncates stderr log. These session/path assumptions must not be copied blindly.
- [`Qn90fEflTextOverlayProbe.csproj`](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/payloads/qn90f/Qn90fEflTextOverlayProbe.csproj) is a deterministic `net6.0` managed executable without an apphost. This fits the general shape of existing target managed/native-interoperability helpers; it is not an S95F validation.
- [`overlay.py`](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/src/samsung_tv_root/overlay.py) limits its public interface to 1–290 seconds and scene JSON to 96 KiB. It invokes `/usr/bin/dotnet` at a fixed QN90F DLL path, removes its staged scene in `finally` with cleanup exceptions suppressed, and checks ready/done text. It returns the notification result and effect-hint ID without rejecting unsuccessful values. A transport timeout raises an error but does not itself prove that the target process died. Its [tests](https://github.com/chris-ritsen/samsung-tv-root/blob/3b97edf3762db7670585d73e29623dc56195bf98/tests/test_overlay.py) use a fake connection; they do not qualify real EFL behavior, focus, timer expiry or plane ordering on the S95F.

Historical target CSFS mappings in `overnight/managed-plugin-inventory.json` include `/usr/lib/libelementary.so.1.25.1`, `libevas.so.1.25.1` and `libecore.so.1.25.1`, plus Ecore Wayland libraries. Existing managed helpers establish .NET/PInvoke feasibility in their own execution contexts. The inspected inventory does **not** prove the needed `libcapi-ui-efl-util.so.0` symbol, all notification/focus-skip exports, the active Wayland session, or that a raw root-launched notification window will preserve Home focus. No target EFL libraries were newly acquired by this work.

## Experimental contrasts

Use one minimal in-process .NET/EFL helper after qualification, with one window and a fixed 16×9 grid of 144 preallocated 120×120 rectangles. Preserve geometry, alpha/opacity policy, notification plane, object count and redraw schedule within each opaque-pixel comparison. Change color on the EFL main loop. Avoid text, fonts, images, file reloads, child processes and app launch. Do not use dynamic-opaque/HWC or screensaver hints. Preload schedules before mapping; log them before the run. Full coverage and actual composition geometry require target verification because 1920×1080 is only the upstream logical canvas.

| Pair | Held fixed | Deliberate intervention | What it can distinguish |
| --- | --- | --- | --- |
| S/P | For You, persistent window, opaque grid, same callback cadence | S repeats candidate gray; P changes gray → sparse/dark tile colors → gray | Content/composition consequence at fixed selected tab versus a timed sham. Mean code values change; this is not a pure workload test. |
| R0/R1 | For You, opaque grid, 72 dark RGB8 tiles and 72 RGB48 tiles | R0 repeats checker; R1 rearranges the same colors into a cluster then restores checker | Spatial distribution at the same declared pixel histogram. This does not assert equal measured luminance/current after processing. |
| T | For You, same window and callback cadence | Opaque candidate scene → all-transparent objects → opaque candidate | Tests exposing native sparse content. Alpha/compositor optimization changes, so interpret separately from the opaque RGB pairs. |
| U | One qualified fully opaque fixed image and window | Apps ↔ For You underneath, via observed stock keys | Tests tab/global policy or hidden rendering workload with the visible composite held fixed. Window/focus/fullscreen-app changes invalidate a selected-tab-only interpretation. |
| D, optional later | For You and an unchanged opaque displayed image | Same image with sparse versus repeated scheduled redraw/damage | Workload/presentation cadence at fixed intended pixels. Requires a qualified way to request/count damage; repeated same-color setters may be optimized away and do not establish actual workload. |

Start with S/P. A checker/spatial pair follows only if useful. Live/video is a separate replication after the For You contrast because it introduces source/video-plane changes. The damaged bottom edge motivates a later top-versus-bottom spatial comparison at fixed declared histogram, but no result from that comparison alone would identify an electrical component.

Use counterbalanced S/P order across separately restored, accepted starts; one proposed initial block is S then P, followed on another observed block by P then S. A fault terminates its exposure and is retained. Do not continue a low-content exposure after a fault just to complete a schedule. More trials are a separate finite session decision, not an automatic search. Absence of fault in one short exposure is weak negative evidence.

Candidate timing is 4 seconds baseline, 8 seconds intervention, 4 seconds planned restoration, with 4 seconds reserved within a separately enforced 20-second helper lifetime. These are design values, not a measured threshold or a basis for overrunning an existing observer. A black or faulted outcome can latch after the triggering scene changes; the later return to gray is a carryover check, not a second independent trial or expected recovery.

## Recovery and the constant-page requirement

**The selected page remains For You throughout every accepted S/P/R/T measurement window. No restart or navigation occurs inside that window.** Independent physical observation, fresh clean RT and the selected-tab/focus checks are required before t0. Keep a candidate stabilizing scene visible while navigating from Apps to For You before t0; then verify it actually established a visible clean For You baseline. Navigation timing is recorded but excluded from the pixel-only contrast.

After a terminal observation, preserve all evidence and end the contrast. Only then use the existing bounded Apps-selected recovery as a separate operational block if needed. It explicitly changes the page to Apps. **The available demonstrated recovery cannot hold For You selected across a reset**, and this design does not claim otherwise. BT is the reason not to assume same-page reset works. Do not modify the recovery helper to reset repeatedly under For You.

For a later trial, use the same Apps context and the same initial overlay scene, then select For You under that fixed scene and verify the same start conditions again. If an overlay survives the reset and stays opaque, its intended visible image could be held constant across Apps selection/restart/reselection; that survival, geometry and Home-state behavior are unqualified today. Even if proved, a controller restart interrupts emitted output and hidden page content changes, so it is a standardized washout, not a same-page causal recovery experiment. All reset and washout intervals are excluded from onset analysis. A persistent latch or unequal time since restart is a block/history covariate, not something a screenshot removes.

## Measurement and acceptance

For G01 / the existing E05 onset gap, couple the scene schedule to **fresh accepted last-clean/first-fault measurements**, including actual ordinary mode, selected limit and aggregate/operands once their exact current-image read contract is centrally qualified. The existing fixed passive observer reads sequential R/M/C/H/L/R windows, with 20-second/80-cycle bounds and timestamps around each USB transfer. Its exact triplet classification is clean `0/0/1` versus faulted `1/0x1001/0`. It is a useful transport/lifecycle pattern, not proof that its current raw windows contain every needed G01 operand or that a nominal 250 ms interval catches the cause.

This report does not build an onset collector or authorize recreating the rejected BI/AL combined recorder. Use accepted existing readers only within their current reviewed contracts; a new synchronized operand recorder is a separately reviewed prerequisite. No overlapping USB consumers or vendor reads while the protocol phase is unknown. A clean sample after BW cannot be borrowed from older BD/BH evidence; fresh RT is required.

Record TV monotonic times for baseline-ready, requested pixel change, EFL callback before/after update, any render/commit callback if qualified, restoration and cleanup. Requested update time is not displayed-frame time. Record control and intervention with identical timing/logging overhead. Validate that the recorder actually covers the transition: capture last-clean through first-fault, and state the before/after transfer intervals and event ordering uncertainty. A fault already present at start is onset-missed, not an intervention success. A missed deadline, stale tab, focus change, short transfer, ambiguous protocol phase, logging loss or unknown process death rejects that trial's causal onset claim.

Use an independent fixed-exposure camera aimed at the physical panel, or a light sensor plus an observer who can identify the scene. Include an external time reference with measured clock-offset uncertainty; a host event marker visible to the camera can bound alignment without adding a bright panel marker. Record the physical black interval separately from the RT transition. An owner timed report is usable with its reaction/clock uncertainty stated. Compositor screenshots/checksums validate intended imagery/window coverage; they **do not measure OLED light, luminance, current or scanout freshness**. A successful overlay-ready line is weaker still.

Keep current source/picture settings, ambient conditions, session timing, fullscreen app ID, selected tab and EFL window identity in each trial record. Obtain bounded passive Home/AVOC/window evidence around the transition to detect FullView/focus/new-home changes. Public lcdon/screen1 and kernel status are useful context, not RT equivalence or proof of light. Preserve visible-but-RT-faulted or black-but-RT-clean counterexamples instead of resetting them to fit the hypothesis.

## Interpretation and deliverables

If opaque RGB changes reproducibly alter fault onset at fixed For You, while timed sham/focus/global Home state stay matched, a **selected-tab-only policy explanation is insufficient**. Pixel processing/composition/electrical-load dependence remains a family of causes; it does not prove purely hardware failure. A spatial same-histogram effect would narrow that family. If Apps/For You still changes onset under the same fully opaque verified image, investigate hidden rendering workload, global Home state and policy; pixels alone are insufficient. If transparent and opaque windows behave differently but opaque RGB pairs do not, composition/occlusion remains a strong confound. Negative short trials do not eliminate content dependence.

Files here are design artifacts only: the JSON plan, three static upstream-format scene examples and the pinned source inventory. The examples have unequal object counts and are **syntax illustrations, not the qualified matched 144-object trial pair**. No target binary, launcher, reset loop or prevention patch was produced. The next concrete decision is whether to qualify the minimal EFL/session/lifetime route and an accepted synchronized onset measurement, not to deploy the upstream QN90F command unchanged.
