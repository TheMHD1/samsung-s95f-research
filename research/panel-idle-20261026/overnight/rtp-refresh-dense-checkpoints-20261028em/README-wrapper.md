# EM intermediate reference-refresh checkpoints

EM is an additive host-built candidate for one centrally coordinated synchronized observation. It preserves frozen DP's R,M,C,P,N,H,L,R order, exact seven address/length definitions, NativeBinding.cs, ReadPair, ReadSet, Run and OnsetKey.cs. All appended values come from windows already read. No new controller request, data write, key call, reset, retry, firmware hook or arbitrary address option is added. Parent coordination and independent artifact review precede any live use; this implementation task performed no target, root or network operation.

The observation is deliberately shorter than DP: a cooperative2-second budget, at most60 complete checkpoint rows,25ms nominal period and2-second per-bulk timeout. Binding qualification still precedes the observation clock. A sent header retains its original pending-IN obligation and partial/failure context. The inherited wrapper keeps root45s/host75s limits. There is **no native40-second process alarm** in frozen DP or EM. These budgets do not promise60 completed cycles or a2-second wall-clock process termination.

A preallocated60×54-byte buffer stores one row only after all eight reads/sixteen transfers complete. The original34-byte prefix is unchanged: classification nibbles, C+7, first/end R+0xc4, H+4/u32, H+28/u16, H+40/fouru16, N+0/u32, full H-pair relative before/after microseconds, and M+0x2a/u16. The new schema is `em-dense-refresh-checkpoints-v1`; count0..60, recordBytes54, canonical Base64 and SHA256 cover exactly count×54 bytes. Rows are implicit cycles1..count, with no duplicated trigger baseline or fabricated incomplete-cycle row.

Build uses the existing .NET6.0.428 SDK with cleared NuGet sources, task-owned DOTNET_CLI_HOME/TMPDIR and no SDK copy/network. The managed DLL is host-built for the unchanged ARM32 native binding. This does not qualify target execution. Source verification, decoder and wrapper suites run normally and with Python `-O`. Frozen deployment/source inventories identify the reviewable artifacts; host-environment/, obj/, caches and review scratch are outside that inventory.


EM requests a 25 ms cycle-start-to-cycle-start period. The unchanged loop subtracts the completed cycle's service time before sleeping. A cycle taking at least 25 ms produces no additional pacing sleep; there is no catch-up burst or guaranteed rate. At zero service delay, 60 cycle starts span 1.475 s and the clean cycle-limit path ends near 1.5 s, before the 2 s cooperative ceiling. The key worker starts only after the first complete clean baseline and runs concurrently, so it can overlap several dense cycles. Actual H pair brackets and the retained per-transfer times establish observed exposure; the requested period alone does not. Higher vendor-read load can affect the system being observed. This trial is not an identical 250 ms control. Even dense sampling can miss the entire refresh sequence and cannot reconstruct every comparator call.

`prepare-readiness.py` is an EM-only cached-metadata derivative of frozen EI's builder. It takes `--wrapper em --wrapper-sha256 <frozen wrapper SHA> --identity <fresh identity JSON> --phase-note <explicit parent premise> --evidence <absolute pinned evidence> --output <fresh directory>`. It sends one ordinary cached identity/FD census request through the pinned root adapter, adds fresh cached evidence, and validates the unique EM readiness schema. This preparation performs no vendor transaction, key or recovery. A coordinator must supply a current USB identity and an honest protocol-phase/lineage premise; no positive endpoint-queue proof is created. The builder was tested only with a mocked root dependency here and has not been executed against a target.
