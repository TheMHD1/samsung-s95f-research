# Source checkpoints for the fixed RTP record capture

DM observes existing controller RAM through twelve fixed read pairs. It introduces no controller logger, firmware patch, breakpoint, producer flag, key or memory write. Current implementation is a host-checked candidate rebased onto DQ native GETDRIVER/statx binding checks after the actual DO zero-vendor probe diagnosed managed lexical symlink resolution. The new D48/record-column headers still require central target qualification. This map supplies source evidence, not a deployment clearance or live image attestation.

All function addresses below are **image1 linked VA**, with file offset=VA+0x40200 in selected package SHA256 `bad60bca4d6064406f14e53da3528d46701ec9c81673f4323db1937f6a2017e0`. Source translator0x1bb74 and root getter0x38fc support CPU0x20000000..<0x20020000→bus0x47000000..<0x47020000 and rootCPU0x20010000. Running-code identity and timing remain conditional. Frozen DE record-verification.json pins seven exact source ranges; source-lineage.json pins that evidence and the DN/DL derivation. No bus mapping is inferred for the packed ringCPU0x20253002.

Ordinal/reset/teardown checkpoints explain why the records cannot be promoted to a timestamped event trace.0xca84..0xcac0 resets sixordinals, counts and history state without erasing record arrays. Frame-end0xb8a8 calls it at0xb964; only when CPU49c is nonzero does that handler clear the first threearrays. Initialization0xcb2c calls reset at0xcb50, clears those same arrays at0xcb86..0xcba6 and zeros x-base. The checked paths leave B/Diff untouched. The nonaggregate wait branch0xc752..0xc780 can subtract source count from an ordinal.0xc220 calls record initialization and clears mode flags at0xc238/0xc23c/0xc240; it is a software reinitialization checkpoint, not proof of a hardware power/reset sequence. Common setter0xc1e0 closes the ordinary gate, while the downstream electrical blanking/rail transition is outside these RAM observations.

The helper itself has a different teardown: once each claimed interface release and opened FD close, no target reset. Receipt acceptance requires both successes; a failed or ambiguous vendor transfer permits no further header. All raw windows, hashes and full request-header-before→reply-data-after brackets are retained. Neither host IN start nor receipt serialization is a device-RAM sampling timestamp.

A useful centrally coordinated comparison, once binding/readiness and these new reads are qualified, is:

1. Capture one DM baseline on stable Apps before a content transition. Retain exact readiness/manifest, raw12windows, per-pair brackets and context; compare start/endR and N as consistency observations, leaving atomicSnapshot and recordEpochProven false.
2. Run the already-qualified DF onset observer with its independent transport/one-Left bounds. Its R,M,C,P,N,H,L,R cycle records software gate transition, source counters, dynamic A/B pointers, aggregate/history/T and score latches. Use the conservative last-clean-header-before→first-fault-data-after interval, conditional on reply freshness. Keep key dispatch timing separate from UI consumption and physical light. DM does not perform the key.
3. Before Mode2 or another reset changes record state, capture one DM postfault if fresh readiness/lineage permits. First compare fault/gate/mode/selector/limits/root and N brackets, then compare all48 tuples and D raw changes against baseline and the DF postfault context. Record differences by byte offset and tuple index; mark indices potentially stale/shared/cleared, never automatically discard them as invalid or call the firstordinal entries current.

Different processes use the same Stopwatch timestamp API, but cross-run ordering still requires same-boot/clock-domain qualification and retained coordinator brackets; dlog wall timestamps require a separate correlation. A stable postfault pair does not backdate its arrays to first fault. Raising a limit to200 also raises the publication mirror on the selected path; a first48 capture samples only48 of512 slots and cannot replace the whole record set after ordinal>48.

This comparison can expose a repeatable concentration in row-like/channel-like metadata, extreme B values outside the inclusive rejection band, large unsigned differences, descriptor changes, or publication saturation with ongoing counts. Such patterns can guide a smaller source/data hypothesis across sparseHome versus populatedApps and HDMI fullscreen versus UgoosHome controls. They do not prove damaged-line causality, fixed-A selection or an electrical mechanism. A physical observation, with an independent time bracket, remains separate.

The next source blind spot is the selected A/B age and physical producer: producer0x18ae8 copies two descriptor-selected0xb60-byte payloads from aperture0x60000000 into the three-slot ring (stride0xb68), while dynamicA selects the remaining slot and B the first fresh slot. Optional A comes from CPU15000/15f10. DF P reveals stored dynamic pointers; D/currentrow still does not expose the selected B header used for the actual branch. No pointer dereference or ring bus alias is included in DM. A future producer/age checkpoint requires independently proven source identity, bounded access and a separate transport qualification. The image0 histogram0x584109a4→SLG→C+7 control bridge is proven separately and must not be substituted for the missing packed-aperture producer.
