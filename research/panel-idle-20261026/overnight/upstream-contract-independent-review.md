# Independent review — upstream AutoDim, PM lock, and maintenance IPC contracts

Review date: 2026-10-26 UTC. This was an offline, read-only audit of the copied
ELF files and the reports/reproducers named below. No TV, network, D-Bus,
remote-key, setter, reboot, service, or firmware action was used.

## Prioritized findings

### 1. Resolved high-severity error: the AutoDim PPI ABI does not have a `+0x90`/`+0x98` mismatch

The original report paired provider literal loads with the immediately nearby
stores and consequently associated the wrong functions with table slots. The
register pipeline in `videoenhancer_impl_set_funcs` proves the following exact
sequence instead:

| Provider instructions | Resolved function | Table slot |
| --- | --- | ---: |
| `0x2a08b2` literal, `0x2a08ca` GOT load, `0x2a08cc` store | `impl_set_netflix_play_state` | `+0x90` |
| `0x2a08bc` literal, `0x2a08d4` GOT load, `0x2a08d6` store | `impl_get_size_of_VE_PPI_Frame_User_Backlight_Param` | `+0x94` |
| `0x2a08c6` literal `0x2ffc`, `0x2a08de` GOT load from `0x5a6ffc`, `0x2a08e0` store | `impl_set_auto_dim_OnOff` | **`+0x98`** |
| `0x2a08d0` literal, `0x2a08e8` GOT load, `0x2a08ea` store | `impl_set_underfit_mode` | `+0x9c` |
| `0x2a08da` literal, `0x2a08f2` GOT load, `0x2a08f4` store | `impl_set_screen_protected_app_launched` | `+0xa0` |

The client wrapper checks and loads the same `+0x98` slot at `0x46f44a3a` and
`0x46f44a4a`, preserves the caller's value in `r4`, restores it to `r0` at
`0x46f44a46`, and tail-calls the slot with `bx r3` at `0x46f44a54`. No table
header adjustment or PPI-version offset is needed. The corrected
`qd-autodim-upstream.md` now states the matching `+0x98` ABI.

### 2. Resolved medium error: the `0x5dc` allocation is the function table, not the backend-data object

`ppi_videoenhancer_get_backend_data()` at `0x46f3e5b4` returns an already
existing backend-data object. `ppi_videoenhancer_get_backend_data_address()`
then executes `malloc(0x5dc)` at `0x46f3e5f6..0x46f3e5fa` and stores the
returned allocation at backend-data `+4` at `0x46f3e604`. Consequently the
`0x5dc` allocation is the function table referenced by the backend-data object;
it is not an allocation of the backend-data object itself.

This distinction matters because it also closes the offset-base question.
`videoenhancer_backend_data_inject()` gets the same backend-data pointer,
loads `[backend_data + 4]` at `0x2ab1b4`, and passes that exact pointer to
`videoenhancer_impl_set_funcs` at `0x2ab1b6`. The provider therefore writes
AutoDim to the exact table from which the public wrapper reads `+0x98`.

The remaining integration chain is statically present and consistent:

* `ppi_videoenhancer_get_backend()` at `0x46f3e664` opens
  `/prd/usr/lib/libave.so` at `0x46f3e6c8`;
* the `libave` init-array relocation at `0x59c4c0` selects
  `videoenhancer_inject()` (`0x91b75`);
* injection reaches `videoenhancer_backend_data_inject()` (`0x2ab168`), fills
  the table, and stores provider version `0x100` (256) at `0x2ab1e0`.

That proves the intended static integration. It does not prove successful
execution during the incident, the current in-memory pointer/table contents,
or any invocation/value.

The corrected `qd-autodim-upstream.md` now uses this function-table wording.

### 3. Medium evidence gap: the AutoDim reproducer does not assert every decisive public-boundary edge

The corrected reproducer now asserts exact provider operands, PIC/GOT math,
the injection table load, and version store. It still checks the public PPI
wrapper only for the presence of some `bx` and `blx` mnemonics within the
function. It does not assert the two `[r3,#0x98]` loads, `mov r0,r4`, or the
`bx r3` at their exact addresses. It also does not assert the static
`dlopen("/prd/usr/lib/libave.so")` route or init-array relocation. Those facts
were independently confirmed above, but the checker can pass if a future
input changes those operands while preserving the broad mnemonic set.

`qd-autodim-upstream.raw.disasm` is explicitly a curated excerpt, not stdout
generated by the reproducer. That is acceptable when labelled, but it must not
be represented as byte-for-byte script output.

### 4. Resolved low evidence gap: the public `GetPowerState` bridge is now asserted by its reproducer

The power-state report's public bridge is correct. In
`dbus_methods_display` (`0x128644`, 656 bytes), the record at `0x128674` is:

```text
name 0x0f3278 -> "GetPowerState"
input signature NULL
output signature 0x0f6d5c -> "s"
callback 0x0005dba4 -> gdbus_get_power_state
```

The callback calls `pm_get_power_state_name` at `0x5dbd0`. That function reads
the same current-index word and seven-row `states` table as
`pm_get_power_state`, returning row word one rather than row word zero. Thus
the report's names `start`, `lcdon`, `lcdoff`, `standby`, `suspend`,
`lowpower`, and `poweroff` genuinely back the public string method.

The corrected `deviced-power-state-contract-reproduce.py` now asserts the
method table symbol, the exact four-word record, the string, callback address,
and `R_ARM_RELATIVE` entries for all three non-null pointers. This closes the
previous reproducibility gap.

### 5. Confirmed: the type-10 standby-lock payload and expiry chain preserve the interval exactly

The type-10 initializer and data flow in `deviced-power-state-contract.md`
match the copied executable:

* init-array slot `0x128220` points to `state_tv_lock_init` (`0x3f5e8`);
* `0x3f604..0x3f60c` registers type 10 with
  `lock_background_standby` (`0x66c4c`);
* `PowerAdapter::lockBGStandby` stores ID then interval as two adjacent words
  at `0x7c264` and `0x7c288`, and calls `device_notify(10,payload)`;
* the handler loads those two words together at `0x66c64` and passes them as
  `pm_lock_state(..., "standby", ID, interval)`;
* for a new lock with positive interval, `pm_lock_state` stores the unchanged
  interval at record `+0x108`, moves it unchanged to `r0`, and calls the PLT
  entry resolving to `g_timeout_add` at `0x66974`;
* its callback is `pm_lock_timer_cb` (`0x65f08`), not the unlock callback;
* record ID 5 selects `device_notify(20,NULL)` at `0x66008..0x66010`;
* the common tail schedules `pm_unlock_timeout` (`0x677f4`) with
  `g_idle_add_full` at `0x65fd8`.

The saved raw power-contract disassembly is exact current reproducer stdout:
both have SHA-256
`a8da12a19b316c66be35b93fb722bab092e3e435611d2b7e9337ffbab8e6bc19`.
No arithmetic, clamp, unit conversion, or alternate timeout callback was found
between the supplied interval and `g_timeout_add`.

### 6. Resolved high-severity maintenance error: the EL D-Bus interface tuple is conventional

The earlier claim that EL used a substring such as `"state"` as its interface
was caused by applying ARM PC-relative math at a literal-load instruction
rather than at the later `add ...,pc` instruction. Exact add-PC resolution is:

| Add instruction | Resolved value | D-Bus role |
| ---: | --- | --- |
| `0x444a47ec` | `org.tizen.system.deviced` | owner/bus name |
| `0x444a47dc` | `/Org/Tizen/System/DeviceD/Display` | object path |
| `0x444a47d8` | `org.tizen.system.deviced.display` | interface |
| `0x444a47c0` | `RequestELSensing` | method |
| `0x444a47ac` | `(i)` | input/reply format used by the wrapper |

The corrected maintenance report and reproducer now use this tuple and the
reproducer passes against the exact copied pair.

### 7. Confirmed attribution constraint: reason `0x4000002a` is not unique to a persisted user request

`qd_display_request_el_sensing(1)` sends the D-Bus request that records
`db/sysman/el_sensing_poweroff=1`; mode `0` instead directly calls
`device_power_request_poweroff(0x4000002a)` at `0x444a481c..0x444a4820`.

In `ELSensing::onPowerOffRequested` the later common reason-writing path has
two entries:

* a nonzero persisted request reaches it only when
  `getPowerOffType()!=6` (`0x755c4..0x755d0`);
* a zero request can independently reach it when `passedRunCycle()` returns
  true (`0x755f8..0x75604`), again subject to the type-6 exclusion.

The common path clears the request at `0x755d8`, saves result 1, then stores
`0x4000002a` through the supplied reason pointer at `0x755e8..0x755ec`.
Therefore a set request is not consumed for power-off type 6, and observing
reason `0x4000002a` would not by itself prove the persisted-user-request route.
The corrected maintenance report now includes both constraints.

The maintenance reproducer asserts the tuple, mode-0 constant, consumer calls,
and final reason store. Its conditional comparisons/branches and the common
helper's exact D-Bus flags/timeout are still manual-inspection facts rather
than explicit test assertions.

### 8. Confirmed conditional expiry notifier; its reproducer covers only part of the stated condition

`pm-lock-expiry-notifier.md` correctly follows ID-5 expiry through notifier 20
to `_OnSensingTimeOut`, selects legacy/Y23 by the holder mode byte, and passes
timeout reason 1 into the respective sensing core. When the sensing state is
2, the core calls object `+0x34`, virtual slot `+0x0c`:

* legacy vtable symbol/address point `0x128a20/0x128a28`, slot address
  `0x128a34`, target `OledDevice::stopELSensing()` at `0x7a6f8`;
* Y23 vtable symbol/address point `0x128ae0/0x128ae8`, slot address
  `0x128af4`, target `OledDeviceY23::stopELSensing()` at `0x80f3c`.

Both targets load `r0=0` and tail-branch through the
`ppi_displaypanel_set_elsensing` PLT entry. This proves a conditional request
to stop EL sensing; it does not prove transport acceptance, measured panel
output, or incident execution.

The expiry reproducer verifies notifier dispatch, wrapper targets, and raw
vtable words, but does not assert the state-2/reason-1 branches or the final
PPI-zero tail branches. The report is factually consistent with independent
disassembly, but these decisive conditions remain outside automated coverage.

The alternative QDDimmingMNT address point is `0x5a094c` (runtime
`0xf711794c`), so it was not the captured object's vptr. The relevant addresses
also land in compatible mappings: vptr in the read-only `libave` mapping, GOT
in its writable mapping, the BSS global in the adjacent anonymous mapping, the
object in anonymous writable memory, and the inner field in `/dev/shm/shm_ave`.

The command read **40 bytes**, not 44: its `dd` counts total ten 4-byte blocks
(`1+1+2+1+1+2+1+1`). The GOT, global, and two-word object header matched in
the before/after reads over reported uptime `35748.44` to `35748.46`. This is
approximately 20 ms at the capture's centisecond display resolution, but it is
not an atomic snapshot; an intervening change-and-return or a field mutation
remains possible. The maps file was also acquired separately about 130 seconds
earlier (`11:26:49` versus the state read at `11:28:59`) under the same
boot/PID guard. The later state command additionally guarded the executable.

This capture is narrower than the stronger acceptance contract in
`qd-runtime-observer-map.md`: it double-reads the three pointer-chain records,
but reads the initialized and AutoDim fields only once. The runtime baseline
states that limitation correctly. The two runtime JSONs also identify the
mapped pathname but do not themselves re-hash the on-device mapped file, so
symbol/offset interpretation relies on the previously established identity of
the copied `libave.so.0.1`.

The earlier retained
`runtime-dimming-first-word-20261026T112537Z.json` shows `od` failing with
`cannot skip past end of combined input` and exit code 1. It supplied no word
used in this conclusion. Subsequent `dd bs=4 skip=...` reads succeeded, and
the final result is based only on their explicitly decoded bytes.

This narrows one former runtime unknown: at that sample, the selected object
was QDDimming rather than QDDimmingMNT, its local initialized gate was nonzero,
and its raw stored AutoDim request field was zero. It does **not** show when or
whether `SetAutoDim` last ran, whether zero was accepted downstream, whether
the field remained zero outside the read interval, what the screen displayed,
or whether the physical OLED emitted light. Physical state was explicitly
unobserved, so the sample is not incident causality or evidence of recovery.

## Integration boundary

The reviewed binaries establish static capabilities and exact conditional
routes. The new sample establishes QDDimming selection and raw field zero only
at its bounded read interval. It does **not** establish that AutoDim, EL
start/stop, the ID-5 timer, or reason `0x4000002a` ran at the observed blackout.
It also does not establish that any PPI request was accepted downstream or
that any route directly shut off physical OLED emission. Caller-supplied
history, timer/notifier presence, power type/state, and onset-aligned physical
output remain incident facts requiring read-only live observation with the
owner present.
