## DN claim ownership correction

The frozen DL production attempt is preserved as a rejected result. Its zero-I/O receipt self-test passed; production opened and successfully claimed interface2, then repeated an unbound-driver guard after that successful claim and rejected a newly present driver binding. The failed receipt did not retain that link's resolved name, so its exact target identity is not claimed here. It returned zero vendor headers/bulk transfers, writeAttempted=false, ReadyForHeader, and released/closed. No threshold mutation occurred.

DN tracks openedFd, claimFd and ownClaim explicitly. Only claim return0 sets ownership. Initial/preclaim identity requires an absent driver; postclaim identity requires a real directory symlink resolving exactly to `/sys/bus/usb/drivers/usbfs`, plus successful own-claim state and the same FD. Preexisting usbfs ownership, another driver, missing/dangling postclaim linkage, mismatched identity or failed claim never grants ownership. Bulk and release additionally require that exact locally tracked claimed FD. A release failure preserves ownership state until an attempted close; acceptance still requires explicit release and close success.

The FD statx check is separate from the initial cached18-byte descriptor read, which advances the file position. Postclaim identity checks do not issue another cached descriptor read or any USB request. The read/write protocol, fixed addresses/values, callback/profile/clean-state gates, one-shot actions, private structured receipts, deadlines and Unknown-phase handling remain inherited from DL. No reset, detach-driver, forced claim, retry or background action is added.

The native fake backend now models a successful claim changing the driver from absent to usbfs. Regression checks require that ordinary lifecycle to pass and require zero vendor headers for preexisting, unexpected, dangling or missing bindings. The same driver-policy function is exercised directly for exact, similar-name, unknown and inconsistent cases. The target-specific canonical usbfs driver path is an upstream-supported platform expectation enforced by DN at runtime; the new helper makes no blanket ownership inference from the driver name alone.
