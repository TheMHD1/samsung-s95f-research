### Arm marker without a competing TV root/controller request

The existing foreground authenticated root adapter returns its whole receipt only after native termination. A new stdout line or a marker file alone is not a live host signal through that interface. Polling a second root request during collector ownership is excluded. Therefore a no-key experiment also needs an explicitly reviewed orchestration delta; it cannot honestly be called wrapper-only.

A minimal proposed route is one **bounded launch request** that starts the exact, supervised native child with private outputs, waits for one exclusive structured marker and returns the marker while that child remains the sole controller owner. Publish the marker only after baseline ring, fresh initialR/M/C, checked logger1 and a complete fullClean baseline; include exact PID/job/stage ownership, native baseline time, source/payload pins, phaseReady and remaining budget. The same initial root command may observe its child's ordinary marker; it sends no additional controller transaction. The host then sends the one already selected Kodi RPC through its separate Ugoos route. No further TV root/USB request occurs until terminal collection.

That route is **proposed, not implemented or qualified**. Required new proof is explicit: exclusive stage/marker/final receipt and added-file tail inventory; exact child ownership and bounded lifetime through host failure; no marker before full admission; bounded marker wait and dispatch age; failed/lost acknowledgement never causes a retry; no orphan logger ownership disguised as success. FN has a cooperative40s budget, not a pre-existing native alarm, so returning a shell while a child runs cannot itself be claimed to provide a hard watchdog. A new supervision mechanism must preserve pending accepted-IN/payload completion and cleanup reserve; killing at40s is not proof of restored gate or known phase. This supervision gap must be closed before implementing that launch route.

An alternative keeps the existing foreground root request and adds a prequalified authenticated host notification channel from a fixed native worker after its full baseline. The host listener receives ARMED and performs the one Kodi RPC without any second TV root request; the native records the acknowledgement separately and retains a bounded worker-join reserve. That adds a network/worker contract and needs review rather than borrowing OnsetKey success labels. No such channel is currently qualified for these helpers.

For either route, malformed/stale/duplicate marker, refused initial context, lost host, delayed trigger, marker published then early native fault, clock failure, short accepted header/payload and restore failure need explicit tests. A successfully returned ARMED marker can become stale before the host receives it; host dispatch timing alone does not prove the actual media frame overlaps a later optional controller read. Report host↔native clock bounds separately and mark exposure unknown/false where the ordering cannot be proved. Media start success is not physical visibility or a caller/FP observation. Unknown transport permits no new header, automatic restore retry, stage cleanup or recovery request; knownReady but refused restoration remains a separate gate-reconciliation obligation for the parent.

The concrete next implementation decision is thus a reviewed **fixed40/no-key native+parser** with an explicit marker/notification ownership contract, not running existing FN/GG with their key merely disabled in prose. No code, target marker, worker, helper or device action is created here.
