# Wake-qualified fixed40 capture: prospective protocol

This is a parent-owned prospective experiment, outside the publication cutoff
at public commit348387af. It is not an execution or a result. FC must first
be frozen and independently reviewed. Source pins and final review references
will be recorded before any target activity for this protocol.

Purpose: exercise the additive pre-native wake/UI logger in a finite fixed40
capture. It improves the recorded entry checkpoint; it does not instrument
the embedded comparison instruction or establish the physical picture.

1. Reconcile the last accepted EX recovery-validation on USB64: completed
   ReadyForHeader, released/closed, exact removed stage and no intervening
   vendor operations. Obtain fresh cached identity/census through the pinned
   readiness builder. A changed instance or unexplained holder stops work;
   no new header is a way to repair uncertain phase.
2. Prepare cached Apps/header through the unchanged DK normal-key routine,
   preserving its raw snapshots and key receipts. This separate preparation
   is accounted independently of FC's one wrapper wake and native one Left.
   Unexpected tabs stop; no blind navigation repair is part of this protocol.
3. Run FC dry first. Verify its frozen manifest, unchanged ER DLL/parser and
   command, fixed40 completed-capture admission, new readiness/result schemas
   and reviewer results. Dry mode must make zero target calls.
4. Execute FC once with the fresh pinned readiness. Its explicit insertion
   occurs after staging, selftests and full pre-invoke census: one VOLUP pair,
   bounded strict Apps/noSaver/CSFS snapshots, then immediate native command
   submission subject to its host-age guard. Preserve raw window listings,
   including ordinary volume OSD. Neither focus, same rendered scene, key
   consumption nor the resulting tab is guaranteed by that predicate.
5. Preserve and independently admit the completed receipt, all retained raw
   windows and wake/dispatch accounting before considering any later
   controller request. Record actual timing and Clean/Quiescent/Faulted
   classifications distinctly. No threshold, lane mask, executable, kernel,
   persistent setting, boot or flash write is part of this experiment.
6. There is no automatic retry, restore or recovery. If the native stage is
   ambiguous, pending or protocol-Unknown, stop without a new header, reset,
   UI action or cleanup assumption. An explicit parent reconciliation may
   use only positively completed evidence and exact owned-stage rules.
7. After a known completed capture, ordinary cached UI queries may record
   the actual selected page. If a stable software fault needs recovery,
   separately qualify the unchanged EB read, Apps navigation and EI40 stock
   MODE2 procedure. One recovery and subsequent fresh identity/EB validation
   remain distinct workflows with their own evidence and results. No second
   recovery is implicit. Finish in cached Apps with sampled clean40 if the
   qualified recovery succeeds; physical light remains unobserved.

This is a measurement improvement, not a matched40/200 causal comparison.
An ordinary volume overlay may change the rendered input. A failed trigger
or clean run cannot prove prevention. Actual comparison operands, selected-A
provenance and the hardware blanking edge remain separate instrumentation
tasks; FD is investigating a distinct stock kernel log route.
