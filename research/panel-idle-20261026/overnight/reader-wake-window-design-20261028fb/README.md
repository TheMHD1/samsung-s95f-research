# Pre-native ordinary-wake checkpoint: design only

Recommendation: create an additive, explicitly named wrapper derivative of ER, keeping the exact native DLL, its eight-read transport, one-Left worker,58-byte layout,2s/56-cycle/25ms settings, exclusive receipts and fixed stage prefix unchanged. Add one visible fixed ordinary VOLUP workflow plus bounded cached-UI settling **after** payload staging, managed fake selftests and the full BEFORE_INVOKE_READY census. Submit the existing native command immediately after the last accepted UI snapshot. No implementation, target/root/network call or frozen-source edit was performed for this design.

This closes the long preparation→staging/selftest/census gap as a recorded checkpoint. It cannot guarantee a continuous no-saver interval, actual focus, an Apps→Live destination, physical light, or that Left was consumed as navigation. State must be described as cached Apps/noSaver/CSFS at the final query, with a measured host scheduling/submission gap. The later Apps+saver observation does not prove the earlier Left was wake-consumed. Conversely, the reported200 leg's23 sampled Clean/Clean above40 contextual witnesses remain software evidence independently of the eventual cached destination; this design does not reclassify or retroactively reject them.

## Exact insertion and dependencies

Frozen ER execute currently stages three payloads, invokes receipt-self-test, strictly admits93/22/79 fake-test counts, performs BEFORE_INVOKE_READY cached identity plus full FD census, then calls run(native). That run builds a guarded root command, rechecks IMMEDIATE_READY without a second full census, and starts dotnet. The new stage belongs between successful full census admission and native intent/submission, while no native device has been opened/claimed and no reader bulk header has been sent.

Use the hash-pinned ordinary navigation module's local wake action only: input_keyevent XF86AudioRaiseVolume down,150ms hold, and one up attempt, recording exact stock binary pin/down/up statuses and raw root response. It is unconditional exactly once for comparability, not retried until wake succeeds. Record the wake intent before submission. A failed or ambiguous down/root response stops; never retry the key or start native after an incomplete/unclassified workflow. Preserve the existing ordinary routine's up attempt after a failed down. No Home, Right, Up, Left, settings/power call or other navigation is added by this insertion; earlier explicit Apps/header preparation remains a separate preregistered step.

After the completed/reaped key pair, use at most10 cached snapshots,250ms between unsuccessful observations, accepting the first snapshot with tab exactly d/apps.tab, no ScreenSaver.dll/ScreenSaverContent.dll window, and the CSFS process window present. Wrong/missing/duplicate tab or malformed/truncated snapshot is terminal, not a navigation-repair branch. Saver/CSFS transient state may settle within that fixed read-only bound; no additional key follows. Preserve every raw command/response, boot/uptime bracket, parsed summary and source hash. The current NAV parser takes the first current-tab row; an additive strict snapshot checker should require exactly one canonical current-tab row before using it for this new admission. This is a narrow parser strengthening, not a change to frozen NAV.

Immediately after acceptance, record host monotonic query-return and native-command-submit timestamps, then invoke the original native command with no intervening upload, selftest, census, navigation, analysis or reset. Its existing IMMEDIATE_READY/device guards still run. Record the actual host gap and require a small explicit host submission-age bound (proposed1s); reject before submission if exceeded. This bounds host scheduling only, not remote command service/start latency or target UI freshness. Record root request start/end and native start/first-header times in their own domains. Do not subtract /proc/uptime or kernel dmesg times from native Stopwatch timestamps without a calibrated mapping. Settle's2.25s scheduled sleep bound excludes root-call latency: each call retains45s remote/75s host limits, so this is finite but not a2.25s hard wall-clock guarantee. A cooperative overall wake/settle budget (proposed10s host monotonic, checked before each new request) may stop new calls; an already blocked call retains its existing outer bound.

## Wrapper shape and accounting

Prefer a short explicit additive wrapper clone over intercepting root.root command strings. The existing execute API takes a root object, but a proxy would hide additional UI calls inside a nominal native call, lacks a stable supported pre-native callback, and returns a frozen result claiming wrapperUiOperations0. Matching a --execute substring or patching closures is not a reviewable dispatch boundary. If a future explicit pre-native callback API is chosen instead, that API must be new, fixed-purpose and fully pinned, not an arbitrary command hook.

New wrapper/readiness/result/manifest schemas and source inventory must bind the wrapper, wake/check helper, NAV module, root adapter and unchanged native checkpoint/parser/three payload hashes. Native checkpoint/schema and /tmp/researcher-er-<32hex> directory prefix must remain ER because the unchanged native receipt validator enforces that prefix; merely renaming the stage to fb would refuse before native work. Use the frozen ER parser from its fixed pinned path (or byte-exact retained copy). No arbitrary path/address/expected-limit parameter is introduced. A future200 counterpart must use the same wake/check protocol but its separate fixed EY native family and existing EY stage prefix, with an independent manifest.

Manifest planned wrapper UI workflows becomes1; native UI workflow remains oneLeft after first full Clean/Clean cycle. Record attempted/completed wrapper workflows and two key child attempts separately, with no executionConfirmed or UI-consumption claim. Accepted wrapper results must truthfully report wrapperUiOperations1, not frozen0. Vendor/header counts remain the original reader counts. A derivative completed-capture admission must bind the new manifest/result schema, native ER parser, wake receipt/strict snapshot receipt, bounded dispatch gap and all-sampled40 controller limits before allowing a later EB read. Frozen ES40 admission cannot be reused with a new wrapper manifest pin unchanged.

A UI refusal occurs before native submission: preserve nativeInvocations0 and the staged payload/selftest files. Existing wrappers retain stages on refusal; do not introduce an unreviewed automatic deletion/reset/retry. A separately reviewed exact-inventory cleanup can handle the known six-file pre-native stage. Once native submission is ambiguous, do not infer nativeInvocations0 from missing output or issue another command automatically. All existing claim, pending-IN, Unknown-stop, key-join, receipt and owned-stage rules remain in force.

## Why a separate bounded UI call is necessary

Actual retained ER native command length is7866bytes, leaving326 under8192; EY is7844, leaving348. Their selftest commands are6180/6158bytes. A complete cached tab/window snapshot plus strict guard cannot safely be appended to the near-cap native command without restructuring or extra staged code. Root response cap remains65536; adding raw window listings to the semantic receipt envelope also consumes its remaining capacity. This design keeps the native command byte-exact and stores ordinary UI receipts in separate bounded root calls. It therefore promises the final recorded cached checkpoint plus explicit submission gap, not a literally atomic UI/native start. If truly same-command cached-state admission is required, stop and design a separate reviewed command split; do not silently drop payload/inventory/device guards or increase caps.
